# 需求分析文档 (Requirement Analysis)

## 项目概述

**项目名称**：PathPal（旅伴）
**课程主题**：基于智能体的个性化旅游系统的设计与实现
**技术栈**：Python Flask + HTML/CSS/JS + Leaflet + JSON

## 当前阶段（Phase 1）功能模块

### 模块一：旅游推荐
- 按热度（popularity）推荐目的地 Top-K
- 按评分（rating）推荐目的地 Top-K
- 按用户兴趣（interests + favorite_categories + preferred_tags）个性化推荐
- 按名称、类别、关键词搜索目的地
- 搜索结果按热度或评分排序

### 模块二：景区/校园内部路线规划
- 仅在用户已进入某个景区或校园后使用
- 基于该目的地绑定的内部地图（internal_map_id）进行路线规划
- 支持四种策略：
  1. 最短距离策略（Dijkstra，边权 = distance）
  2. 最短时间策略（Dijkstra，边权 = time，考虑 congestion）
  3. 交通工具最短时间策略（walk / bike / sightseeing_car）
  4. 混合交通策略（每条边选择最快交通方式）
- 支持多点路径规划（多目标串联）
- 校园支持：步行、自行车、混合
- 景区支持：步行、电瓶车、混合

### 模块三：景区/校园内部场所查询
- 仅在用户已进入某个景区或校园后使用
- 查询指定地点附近的服务设施
- 排序依据为道路图上的最短路径距离（非直线距离）
- 支持按设施类别筛选

## 明确不做（当前阶段排除）

| 序号 | 排除功能 | 原因 |
|------|----------|------|
| 1 | 旅游日记管理 | 超出当前阶段范围 |
| 2 | 旅游日记交流 | 超出当前阶段范围 |
| 3 | 美食推荐 | 超出当前阶段范围 |
| 4 | 完整登录注册 | 仅用 user_id 模拟，不实现认证系统 |

| 7 | 用户家到景区大门 | 不做外部路线规划 |

## 核心边界约束

### 空间边界
- 路线规划只发生在 **景区/校园内部道路图** 上
- 每个目的地绑定一个 `internal_map_id`，规划和查询都在该地图内部进行
- **严禁跨 internal_map_id 规划**

### 数据边界
- 目的地数量 >= 200
- 内部地图模板数量：少量（3-5 个），200 个目的地可复用
- 每个内部地图内节点数量 >= 20（建筑物 + 景点）
- 服务设施数量 >= 50（类别 >= 10 种）
- 内部道路边数 >= 200
- 用户数量 >= 10

### 技术边界
- 核心数据存储：JSON 文件（不使用数据库）
- 核心算法：自行实现（排序、查找、最短路、Top-K），不依赖第三方库
- 地图可视化：Leaflet

### 交通策略边界

**校园（type=campus）**：
- 可选交通：walk、bike、mixed
- 自行车默认在校园内任何地点可用
- 但自行车只能走 `allowed_transport` 包含 `bike` 的道路
- 上车即走（无需等待）

**景区（type=attraction）**：
- 可选交通：walk、sightseeing_car、mixed
- 电瓶车只能走 `allowed_transport` 包含 `sightseeing_car` 的固定路线
- 上车即走（无需等待）

**混合策略（mixed）**：
- 对每条边，在 `allowed_transport` 中列出的交通工具里，选择耗时最短的方式
- 返回结果中每段路径需标明实际使用的交通工具

## 性能要求

- 单次 Dijkstra 运行：在 200 条边、数十个节点的图上，应在毫秒级完成
- Top-K 推荐：不得使用完整排序后切片，需自行实现 Top-K 算法
- 附近查询：需对每个候选设施运行 Dijkstra（或一次多源 Dijkstra 预处理）

## 测试要求（后续阶段）

- 使用 pytest 框架
- 测试数据使用独立的小规模 fixture JSON
- 覆盖：模型层、算法层、服务层、路由层
